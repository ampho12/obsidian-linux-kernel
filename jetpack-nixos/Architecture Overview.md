

Overview

jetpack-nixos turns NVIDIA's closed-source L4T (Linux for Tegra) binary releases into first-class Nix derivations. It
supports three JetPack generations (5/6/7) from a single codebase and integrates with nixpkgs via a composable overlay and
NixOS module system.

NVIDIA CDN (debs, BSP tarballs)
        ↓
sourceinfo/  ─── fetches + hashes
        ↓
buildFromDebs.nix  ─── unpacks, normalises, patchelf
        ↓
pkgs/l4t/*.nix  ─── per-package fixups
        ↓
mk-overlay.nix  ─── assembles the full package scope
        ↓
overlay.nix  ─── routes by JetPack/CUDA version
        ↓
flake.nix  ─── NixOS configs, flash scripts, outputs
        ↓
modules/  ─── hardware.nvidia-jetpack.* NixOS options

1. Inputs and Dependency Fetching

1.1 Flake inputs

| Input                 | Purpose                                                  |
|-----------------------|----------------------------------------------------------|
| nixpkgs (nixos-25.05) | Base package set                                         |
| cuda-legacy           | Upstream CUDA packages; applied as a lower overlay layer |
| middleware            | Gradient robotics services (imported as a NixOS module)  |
| seeed-l4t             | Optional Seeed-specific kernel source tree               |

1.2 NVIDIA package fetching — sourceinfo/

NVIDIA ships L4T as .deb packages in three Debian-style repositories on their CDN:

https://repo.download.nvidia.com/jetson/
  ├── common/          # Shared packages (multimedia API, CUPVA, OpenCV, CUDA libs)
  ├── t234/            # SoM-specific packages for Xavier/Orin (L4T 35/36)
  └── som/             # Renamed SoM repo for L4T 38+

sourceinfo/default.nix loads a pinned JSON manifest per L4T version and converts every entry into a fetchurl call:

debsJSON = lib.importJSON ./r36.4-debs.json;

debs = lib.mapAttrs (repo: pkgs:
  lib.mapAttrs (name: pkg: pkg // {
    src = fetchurl {
      url = "${baseURL}/${repo}/${pkg.filename}";
      sha256 = pkg.sha256;
    };
  }) pkgs
) debsJSON;

The JSON files (r35.6-debs.json, r36.4-debs.json, r38.2-debs.json) are generated by sourceinfo/debs-update.py, which scrapes
 NVIDIA's Packages.gz index files. Pinning via SHA256 gives fully reproducible builds — the actual deb bytes are only
downloaded when you build a package that needs them.

sourceinfo/ also fetches git repositories (kernel source, OP-TEE, etc.) via gitrepos-update.py + fetchgit, used for the
kernel and UEFI builds. These are not needed for the runtime library packages in l4t-sdk.

1.3 BSP tarball — mk-overlay.nix

The Board Support Package (bootloader, flash tools, devicetree) is fetched separately:

bspSrc = final.fetchurl {
  url = "https://developer.download.nvidia.com/embedded/L4T/r${major}_Release_v${minor}.${patch}/release/Jetson_Linux_R${ver
sion}_aarch64.tbz2";
  hash = bspHash;
};

Extraction uses bzip2_1_1 (a pinned older bzip2) because NVIDIA's archives are incompatible with newer bzip2 versions due to
 an upstream compression bug.

2. Building Packages from Debs — buildFromDebs.nix

This is the central abstraction. All L4T packages call it with at minimum a pname:

buildFromDebs {
  pname = "nvidia-l4t-core";
  buildInputs = [ expat libglvnd ];
}

Under the hood it is a stdenv.mkDerivation that:

1. Unpacks all .deb sources using dpkg-deb -x
2. Normalises the directory layout (see §3)
3. Runs autoPatchelfHook to rewrite hardcoded RPATHs
4. Installs with cp -r . $out

2.1 Directory normalisation (postPatch)

NVIDIA debs follow Debian conventions; Nix expects a flat lib/, include/, share/ layout. The postPatch block handles this
mechanically:

| Original path           | Nix path              | Reason                         |
|-------------------------|-----------------------|--------------------------------|
| usr/lib/…               | lib/…                 | Debian FHS prefix              |
| local/…                 | …                     | Some debs use /usr/local       |
| cuda-12.6/…             | …                     | Version-specific CUDA prefix   |
| lib/aarch64-linux-gnu/… | lib/…                 | Multiarch suffix               |
| lib/tegra/…             | lib/…                 | Tegra-specific subdir          |
| lib/nvidia/…            | lib/…                 | Nvidia-specific subdir         |
| lib64                   | lib64 → lib (symlink) | Many debs use lib64            |
| etc/ld.so.conf.d/       | (deleted)             | Would pollute the linker cache |

2.2 autoPatchelf

NVIDIA binaries have RPATH entries pointing to system paths like /usr/lib/aarch64-linux-gnu. autoPatchelfHook rewrites these
 to Nix store paths by matching against buildInputs. It also adds missing dependencies discovered at link time.

2.3 Cross-compilation search paths

When building for aarch64 on an x86_64 host, the target libc lives in a subdirectory like
${stdenv.cc.cc.lib}/aarch64-unknown-linux-gnu/lib/. An extra postFixup step adds this to autoPatchelf's search path so it
can find libgcc_s.so and similar when cross-compiling:

postFixup = lib.optionalString (autoPatchelf && stdenv.hostPlatform != stdenv.buildPlatform) ''
  addAutoPatchelfSearchPath ${stdenv.cc.cc.lib}/*/lib/
'';

3. Per-Package Fixups — pkgs/l4t/*.nix

Most packages need no more than a buildInputs list. A few require specific surgery.

3.1 l4t-cuda — ptxjitcompiler extraction

NVIDIA inexplicably ships libnvidia-ptxjitcompiler.so inside the 3D-core deb rather than the CUDA deb. l4t-cuda extracts it
at build time:

dpkg --fsys-tarfile ${debs.t234.nvidia-l4t-3d-core.src} \
  | tar -xO ./usr/lib/aarch64-linux-gnu/nvidia/libnvidia-ptxjitcompiler.so.540.4.0 \
  > lib/libnvidia-ptxjitcompiler.so.540.4.0

It also creates the libcuda.so.1 and libcuda.so symlinks that NVIDIA omits, and injects libnvcucompat.so as a DT_NEEDED
entry via patchelf (libcuda dlopens it but doesn't declare it).

3.2 l4t-3d-core — ICD JSON paths and NvOsLibraryLoad

ICD JSON paths. Vulkan and EGL require JSON files that point to the library file. NVIDIA's debs use relative paths which
work on a normal system but break in the Nix store. Fixed with sed:

sed -i -E "s#(libGLX_nvidia)#$out/lib/\\1#" share/vulkan/icd.d/nvidia_icd.json
sed -i -E "s#(libEGL_nvidia)#$out/lib/\\1#" share/glvnd/egl_vendor.d/10_nvidia.json

NvOsLibraryLoad / RUNPATH problem. libnvos.so exports a wrapper called NvOsLibraryLoad that several nvidia libraries use
instead of calling dlopen directly. The problem: when dlopen is called from inside libnvos.so, the dynamic linker uses
libnvos.so's own RUNPATH, not the RUNPATH of the calling library. This means libEGL_nvidia.so cannot find its own
dependencies.

Fix: make a per-package copy of libnvos.so with its own soname and RUNPATH:

cp ${l4t-core}/lib/libnvos.so lib/libnvos_3d.so
patchelf --set-soname libnvos_3d.so lib/libnvos_3d.so

# Rename the symbol in all 3d-core libraries
echo "NvOsLibraryLoad NvOsLibraryLoad_3d" > remapFile
patchelfUnstable "$lib" \
  --rename-dynamic-symbols remapFile \
  --replace-needed libnvos.so libnvos_3d.so

l4t-multimedia applies the same pattern with libnvos_multimedia.so.

3.3 l4t-multimedia — libv4l rebuild

NVIDIA's V4L2 wrapper has the plugin directory path (/usr/lib/aarch64-linux-gnu/libv4l/plugins/nv) hardcoded at compile
time. Since that path doesn't exist in the Nix store, libv4l won't load the Nvidia V4L2 codec plugins.

Fix: rebuild libv4l from the upstream NixOS package with a patch that replaces the hardcoded LIBV4L2_PLUGIN_DIR macro. A
placeholder Nix store path is used during compilation to avoid a circular dependency, then fixed up with sed after the fact:

postPatch = postPatch + ''
  substituteInPlace lib/libv4l2/v4l2-plugin.c \
    --replace LIBV4L2_PLUGIN_DIR \
    '"/nix/store/00000000000000000000000000000000-${l4t-multimedia.name}/lib/libv4l/plugins/nv"'
'';

# Later, in l4t-multimedia's postPatch:
sed -i "s#/nix/store/00000000000000000000000000000000-${l4t-multimedia.name}#$out#" \
  lib/libnvv4l2.so lib/libnvv4lconvert.so

3.4 l4t-camera — dlopen override

libnvscf.so and libnvargus_socketclient.so have the EGL library path hardcoded as a string literal passed to dlopen:

dlopen("/usr/lib/aarch64-linux-gnu/tegra-egl/libEGL_nvidia.so.0", RTLD_LAZY)

That path doesn't exist on NixOS (the library lives under /run/opengl-driver/lib/). This is handled by the dlopen-override
mechanism (see §4).

---
4. dlopen-override — Runtime Path Interception

The problem

Some Nvidia libraries call dlopen with absolute system paths baked in as string literals. These cannot be fixed by patchelf
(which only handles ELF metadata) or RPATH (which only applies to DT_NEEDED entries).

The mechanism

A small C shim is compiled that wraps dlopen and redirects specific paths at runtime:

// dlopenoverride.c (template — paths filled at build time)
const char *old_paths[] = { "@oldpaths@" };
const char *new_paths[] = { "@newpaths@" };

void *__dlopen(const char *filename, int flag) {
    for (int i = 0; i < num_paths; i++) {
        if (strcmp(filename, old_paths[i]) == 0) {
            filename = new_paths[i];
            break;
        }
    }
    return dlopen(filename, flag);
}

The Nix builder compiles a unique dlopen-override.so per rewrite mapping (uniqueness via builtins.hashString on the rewrite
set), then uses patchelfUnstable to inject it into the target library:

patchelf $target_lib \
  --clear-symbol-version dlopen        # Remove GLIBC version constraint on dlopen symbol
  --rename-dynamic-symbols remap       # dlopen → __dlopen_<hash>
  --add-needed dlopen-override.so      # Link the shim
  --add-rpath ${dlopen}/lib            # Find the shim at runtime

The --clear-symbol-version step is required because when you rename the dlopen symbol to __dlopen, the GLIBC version tag
(GLIBC_2.17) that came with the original dlopen would follow it. The compiled shim's dlopen call would then have a version
mismatch. Clearing the version avoids this.

Used by: l4t-camera for libnvscf.so and libnvargus_socketclient.so, both redirecting libEGL_nvidia.so.0 from
/usr/lib/aarch64-linux-gnu/tegra-egl/ to /run/opengl-driver/lib/.

5. Overlay Architecture — overlay.nix + mk-overlay.nix

5.1 Version routing

overlay.nix creates three JetPack package scopes and a version-selector alias:

| Attribute       | L4T                               | CUDA     | Driver  |
|-----------------|-----------------------------------|----------|---------|
| nvidia-jetpack5 | 35.6.2                            | 11.4.298 | null    |
| nvidia-jetpack6 | 36.4.4                            | 12.6.10  | 540.4.0 |
| nvidia-jetpack7 | 38.2.1                            | 13.0.2   | 580.00  |
| nvidia-jetpack  | ← default, chosen by CUDA version |          |         |

The default selection is CUDA-driven so that pkgs.cudaPackages.blarg automatically receives the matching JetPack version —
preventing a mismatch where, say, CUDA 12.6 libraries are linked against JetPack 5 runtime libraries.

5.2 Package scope construction — mk-overlay.nix

Each JetPack version uses makeScope to create an isolated package namespace:

makeScope final.newScope (self: {
  buildFromDebs = pkgs.callPackage ./pkgs/buildFromDebs.nix { inherit debs ...; };
  dlopenOverride = pkgs.callPackage ./pkgs/dlopen-override {};

  l4t-core      = self.callPackage ./pkgs/l4t/l4t-core.nix {};
  l4t-cuda      = self.callPackage ./pkgs/l4t/l4t-cuda.nix {};
  l4t-multimedia = self.callPackage ./pkgs/l4t/l4t-multimedia.nix {};
  # ... all other l4t packages
})

self.callPackage resolves arguments from the scope first, then falls back to pkgs. This means l4t-multimedia.nix can declare
 { buildFromDebs, l4t-core, l4t-cuda, ... } and get the scope's versions automatically.

5.3 CUDA package scope

CUDA packages (cuDNN, TensorRT, cuBLAS, etc.) are built in a separate makeScope that extends cuda-legacy's package set with
JetPack-specific packages from pkgs/cuda-packages/ and pkgs/cuda-extensions/. The scope provides buildFromDebs, debs, and
version helpers to all CUDA packages.

6.1 Module hierarchy

  ├── flash-script.nix       ← generates flash-*.sh scripts
  ├── graphics.nix           ← OpenGL/EGL/Wayland/X11 setup

  ├── nvpmodel.nix           ← power model service
  ├── nvfancontrol.nix       ← fan control daemon
  ├── capsule-updates.nix    ← UEFI firmware capsule updates
  ├── nvidia-container-toolkit.nix ← Docker/container runtime
  └── optee.nix              ← OP-TEE trusted execution

6.2 Key options

hardware.nvidia-jetpack = {
  enable        = true;
  majorVersion  = "6";              # JetPack 5, 6, or 7
  som           = "orin-nx";        # orin-agx, orin-nx, xavier-agx, ...
  carrierBoard  = "devkit";
  kernel.realtime = false;          # PREEMPT_RT patches
  maxClock      = false;            # Lock to max CPU/GPU frequency
};

6.3 What the module wires up

- Kernel: Selects the JetPack-built kernel (or RT variant), applies device-specific out-of-tree modules
- Boot parameters: nvidia.rm_firmware_active=all, console settings, clk_ignore_unused (required on L4T 38+)
- Initrd modules: Per-version list of modules needed before pivot-root (xhci-tegra, nvme, phy-tegra-xusb, etc.)
- Firmware: hardware.firmware gets l4t-firmware (and l4t-xusb-firmware on L4T < 38)
- Services: jetson_clocks if maxClock = true; nvargus-daemon, nvpmodel, nvfancontrol
- Tooling: Adds l4t-tools (tegrastats, jetson_clocks) and nvidia-smi (L4T 36+) to the system path

6.4 nvargus-daemon

The Argus camera daemon is a userspace process that owns the ISP hardware. Applications connect to it via a socket and
request frames rather than accessing the sensor directly. The module configures it as a systemd service and provides an
ispPkgs option for injecting vendor-specific ISP tuning files into /var/nvidia/nvcam at boot time.

8. Cross-Compilation

All L4T packages are aarch64-linux targets, but the build machine is typically x86_64-linux. This works because:

1. NVIDIA's debs are already aarch64 binaries. dpkg-deb -x runs on x86_64 but only unpacks — no compilation. The extracted
.so files are aarch64 ELF.
2. ELF manipulation tools are platform-agnostic. patchelf and dpkg running on x86_64 can read and modify aarch64 ELF files
without issue.
3. autoPatchelfHook cross-compilation shim. The hook is told where to find aarch64 libgcc_s.so via the extra
addAutoPatchelfSearchPath call in postFixup.
4. buildPackages.patchelfUnstable. Used explicitly for the more complex patchelf operations (symbol renaming) to ensure the
tool itself runs on the build host, not the target.

Flash scripts are only built for x86_64-linux because NVIDIA's tegrarcm_v2 flashing binary is x86_64-only.

Boot flow: 

● The Jetson boot flow has multiple stages, each with its own firmware and configuration:

  Power On
    │
    ├─ Boot ROM (in silicon, immutable)
    │    Loads MB1 from QSPI
    │
    ├─ MB1 (Microboot 1)
    │    - First software stage, runs on BPMP (Boot and Power Management Processor)
    │    - Configures DRAM timing, pinmux, pad voltages, clocks, PMIC
    │    - Needs its config BEFORE DRAM is up → stored as BCT (Boot Configuration Table)
    │    - MB1 BCT DTS files: PINMUX_CONFIG, PMC_CONFIG, DEVICE_CONFIG, SDRAM timings
    │    - These get compiled into a binary BCT blob and stored in QSPI alongside MB1
    │
    ├─ MB2 (Microboot 2)
    │    - Runs on BPMP after DRAM is initialized
    │    - Loads all sub-firmwares (SPE, RCE, DCE, APE, XUSB, PVA)
    │    - Reads carrier board EEPROM ← this is where your J501 fails
    │    - Sets up carveouts, security, prepares CPUBL params
    │    - MB2 BCT: misc config, EEPROM addresses, FSI VMON thresholds
    │
    ├─ UEFI (runs on CPU/CCPLEX)
    │    - Full UEFI firmware (EDK2-based)
    │    - Loads device tree (DTB), kernel, initrd
    │    - This is where YOUR DTB matters
    │    - Hands off to bootloader (systemd-boot)
    │
    └─ Linux kernel + NixOS

  Why DTS for BCTs? NVIDIA uses DTS as a human-readable format that gets compiled into binary BCTs by mkbctpart during the signing step. It's not a real device tree — it's just borrowing the DTS syntax as a
  structured config format. The MB1 BCT DTS describes hardware parameters (pin assignments, DRAM timings) and the MB2 BCT DTS describes boot-time behavior (EEPROM probes, power monitoring thresholds).

  Why separate MB1 and MB2?
  - MB1 runs before DRAM — it literally can't read a DTB from memory because memory isn't configured yet. Its config must be in QSPI flash as a compact binary BCT.
  - MB2 runs after DRAM is up but before the CPU. It handles firmware loading and hardware discovery (EEPROM).
  - UEFI is the first stage on the actual CPU. This is where your custom DTB gets loaded and passed to Linux.

  So: MB1 BCT configures the electrical layer (pins, voltages, DRAM), MB2 BCT configures the firmware layer (EEPROM, security, carveouts), and the DTB configures the OS layer (peripherals, cameras, CAN, GPIO).

❯ so bct is basically a dtb?

● Essentially yes — same DTS source format, compiled the same way with dtc, but used for a completely different purpose.

  ┌───────────────┬───────────────────────────────────────────────┬─────────────────────────────────────────┐
  │               │                      BCT                      │                   DTB                   │
  ├───────────────┼───────────────────────────────────────────────┼─────────────────────────────────────────┤
  │ Source format │ .dts / .dtsi                                  │ .dts / .dtsi                            │
  ├───────────────┼───────────────────────────────────────────────┼─────────────────────────────────────────┤
  │ Compiled by   │ mkbctpart (wraps dtc)                         │ dtc                                     │
  ├───────────────┼───────────────────────────────────────────────┼─────────────────────────────────────────┤
  │ Stored in     │ QSPI flash (alongside firmware)               │ ESP partition or QSPI                   │
  ├───────────────┼───────────────────────────────────────────────┼─────────────────────────────────────────┤
  │ Read by       │ MB1/MB2 firmware (BPMP)                       │ UEFI → Linux kernel                     │
  ├───────────────┼───────────────────────────────────────────────┼─────────────────────────────────────────┤
  │ Describes     │ Hardware init params (pins, DRAM, I2C probes) │ OS-visible devices (cameras, CAN, GPIO) │
  └───────────────┴───────────────────────────────────────────────┴─────────────────────────────────────────┘
